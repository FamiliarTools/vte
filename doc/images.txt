║ VTE images (SIXEL)  ║
╚═════════════════════╝

This describes how an image received via SIXEL is stored, moved, drawn and
freed. Only the model is here; the SIXEL parser itself is in sixel-parser.hh
and sixel-context.cc and is not discussed.

Every statement below is meant to be checkable against the code or against a
test in src/ring-test.cc, src/image-contract-test.cc or src/tests/sixel/. Where
a test names the behaviour, its name is given.

Every command quoted in this document is run from the top of the source tree.
They are written as `git grep`, and with LC_ALL pinned where a shell glob would
otherwise decide the order, so that the output below each one is what the
command produces under any shell and any locale - not only under the one it was
first written in. `git grep --show-function` prints the enclosing function
before each HUNK, so its headers are the SET of functions the hits live in and
not one header per hit; where the count matters it is asked for separately.


The cell is the image
═════════════════════

An image is not an object floating over the grid at a pixel position. It is a
rectangle of CELLS, and each of those cells carries, in its own attributes, the
name of the piece of the picture it holds.

Three things make up that name, and they are packed into exactly 32 bits, which
is the width of VteCellAttr::m_link:

	pool_id  : 14	which image
	tile_row :  9	which cell row OF THAT IMAGE this cell is
	tile_col :  9	which cell column OF THAT IMAGE this cell is

See vte::image::Ref in src/image-ref.hh. The tile coordinates are relative to
the image and never to the screen, so a cell keeps naming the same piece of the
picture wherever its row is moved to. pool_id 0 is reserved for "no image", so
a zeroed reference names nothing (/vte/image/ref/zero-is-not-an-image).

The widths are not arbitrary. They cover the largest image the parser will
admit, laid out against the smallest cell it may be laid out against:

	cols = ceil(VTE_SIXEL_MAX_WIDTH  / VTE_SIXEL_CELL_MIN_WIDTH)
	rows = ceil(VTE_SIXEL_MAX_HEIGHT / VTE_SIXEL_CELL_MIN_HEIGHT)

which at 2048x2052 over a 4x8 minimum cell is 512 columns and 257 rows, both
inside 9 bits. static_asserts in image-ref.hh hold this, and
/vte/image/ref/covers-max-legal-image exercises it.

m_link is a discriminated union: the same 32 bits are either a hyperlink index
or an image reference. VTE_ATTR_IMAGE (src/attr.hh) is the tag. It is a real
attribute bit, so it is persisted with the rest of the attributes when a row is
frozen, and the reader can tell which member is live without any out-of-band
state. It sits deliberately OUTSIDE VTE_ATTR_ALL_SGR_MASK so that
reset_sgr_attributes() cannot strip the tag off a cell whose m_link still holds
an image reference, which would reinterpret those bits as a hyperlink index
(/vte/cell/attr/image-tag-survives-sgr-reset). The union is reached only
through accessors that assert on the tag - hyperlink_idx() asserts !image(),
image_ref_raw() asserts image() - so a caller that has not decided which one it
is holding does not compile into a silent misread.

The cell's character is U+FFFC OBJECT REPLACEMENT CHARACTER. Placing an image
erases the cells in its area and writes U+FFFC into them
(/vte/ring/image-pool/cells-hold-object-replacement). Two consequences follow
from that one choice. The cell is never EMPTY, which matters because an empty
cell is indistinguishable from one the image never covered, and the ring uses
cell contents to decide what a row still holds. And clipboard, selection and
the screen reader are correct by construction: they read the character, and
U+FFFC is the character the Unicode standard has for "an object is here".

The converse is enforced in the other direction too. cell_for_copy() in
vteseq.cc drops both the reference and the U+FFFC when a cell is copied, so a
copy never claims a tile of an image whose pixels are somewhere else.


The stripe
══════════

A STRIPE is one tile row of one image: same pool_id, same tile_row. Ref has
same_stripe() for it (/vte/image/ref/stripe-identity).

The stripe is the unit of a RUN, in two places:

  - VteCellAttr::same_for_stream() (src/cell.hh) treats two image cells as
    sharing an attribute record when they are in the same stripe. The tile
    COLUMN is deliberately not part of that test: a stripe is contiguous, so
    the column is recovered on thaw by counting from the run's first cell, and
    including it would encode what the reader can derive.

  - the draw (Terminal::draw in src/vte.cc) extends a draw run over cells of the
    same stripe whose tile columns are still consecutive, and stops at a gap,
    because a gap means a cell in the middle was overwritten and must not be
    painted. This is BOTH arms: the run loop is under `#if WITH_SIXEL` only, and
    the `#if VTE_GTK` split below it covers just the final blit - a cairo surface
    on GTK3, a GdkTexture on GTK4.

The stripe is NOT the unit of lifetime. Lifetime is per IMAGE: m_image_map,
image_gc(), image_gc_region() and drop_images_before() all work on whole
Images. Nothing in the tree frees one tile row of an image and keeps another.

Those three are not the whole of it. m_image_map owns the Images (it is the
only map of unique_ptr; m_image_by_top_map holds bare pointers), so every free
is an erase or a clear on it, and there are five such sites:

    $ LC_ALL=C git grep --show-function -e 'm_image_map\.\(erase\|clear\)' -- 'src/*.cc' 'src/*.hh'
    src/ring.cc=Ring::image_gc_region() noexcept
    src/ring.cc:                        rit = image_map_type::reverse_iterator{m_image_map.erase(std::next(rit).base())};
    src/ring.cc=Ring::image_gc(vte::image::Image const* exempt) noexcept
    src/ring.cc:                m_image_map.erase(victim);
    src/ring.cc=Ring::erase_image(Ring::image_by_top_map_type::iterator it) noexcept
    src/ring.cc:        m_image_map.erase(priority);
    src/ring.cc=Ring::reset()
    src/ring.cc:        m_image_map.clear();
    src/ring.cc=Ring::append_image(vte::Freeable<cairo_surface_t> surface,
    src/ring.cc:                m_image_map.erase(it);

The last of them is append_image()'s pool-allocation-failure path. Line numbers
are deliberately not written down here, because a line number is stale the
moment anything above it moves.

erase_image() is a helper rather than a policy, and it has nine call sites:

    $ LC_ALL=C git grep -c '= erase_image(it)' -- src/ring.cc
    src/ring.cc:9

They live in seven functions:

    $ LC_ALL=C git grep --show-function -e '= erase_image(it)' -- src/ring.cc | grep -v '^src/ring\.cc:'
    src/ring.cc=Ring::drop_images_before(row_t row) noexcept
    src/ring.cc=Ring::drop_images_after(row_t row) noexcept
    src/ring.cc=Ring::drop_images_torn_by_rewrap(column_t columns) noexcept
    src/ring.cc=Ring::erase_images_in_rect(long top,
    src/ring.cc=Ring::shift_images_for_insert(row_t position) noexcept
    src/ring.cc=Ring::shift_images_for_remove(row_t position) noexcept
    src/ring.cc=Ring::rewrap_images_in_range(Ring::image_by_top_map_type::iterator& it,

Seven headers for nine calls, so some function holds more than one; which one
is not established by these commands and nothing here rests on it.

So the policies that decide an image should go are: the memory and count budget
(image_gc()), rows leaving either end of the ring (drop_images_before(),
drop_images_after()), being invisible (image_gc_region()), the user erasing the
cells (erase_images_in_rect()), rewrap (drop_images_torn_by_rewrap(),
rewrap_images_in_range()), insert and remove shifting an image off the ring
(shift_images_for_insert(), shift_images_for_remove()), a reset (reset()), and
running out of pool ids at placement time (append_image()).

image_gc_region() is the one easily missed: append_image() runs it on every
placement, and it walks m_image_map newest-first accumulating a cairo_region_t
of the rectangles it has seen, freeing any image whose own rectangle is already
contained in that union - an image drawn completely over by later ones.

The pixels are spilled first on exactly two of those paths, and it is a shorter
list than the freeing one:

    $ LC_ALL=C git grep -n 'spill_image(' -- 'src/*.cc' 'src/*.hh' | wc -l
    7

Seven lines, of which the definition, its declaration and three comments are
not calls. Ask for the calls alone - a spill_image() opening a statement - and
for the function each one sits in:

    $ LC_ALL=C git grep --show-function -e '^ *spill_image(' -- 'src/*.cc' 'src/*.hh'
    src/ring.cc=Ring::image_gc(vte::image::Image const* exempt) noexcept
    src/ring.cc:                spill_image(image.get());
    src/ring.cc=Ring::drop_images_before(row_t row) noexcept
    src/ring.cc:                spill_image(image);

Two calls, in image_gc() and in drop_images_before(). No ordinal into the
seven-line listing is needed, and none is claimed.

Every other path above frees without spilling, image_gc_region() among them.
What image_gc() and drop_images_before() have in common is that the row may yet
be read back - the eviction is for memory, or the row has gone to the
scrollback. This document does not establish, path by path, why each of the
remaining ones is safe not to spill; that was observed, not proved.


Where the bytes live
════════════════════

The ring already has three streams for scrollback - text, attr and row - and
the image model adds to both of those layers rather than inventing a cache
directory.

The image REFERENCE goes into the ATTR stream. An attribute record is a
CellAttrChange, then the hyperlink data, then two bytes repeating the hyperlink
length so the record can be walked backwards. That trailing length has to stay
last, because thaw_row()'s truncating pass walks the stream backwards and reads
it at (offset - 2). So the image reference cannot simply be appended after it.
Instead the trailer carries the flag: hyperlink lengths are bounded far below
0x8000 by VTE_HYPERLINK_TOTAL_LENGTH_MAX, so the high bit is free and says
whether a StreamImageRef (src/ring.hh) precedes the trailer. The record stays
self-describing in both directions, and attr_record_stride() is the one place
the stride is computed, because the freeze, thaw, truncate and rewrap paths each walk
these records independently, over the seven lines of src/ring.cc that name it:

    $ git grep -c attr_record_stride -- src/ring.cc
    src/ring.cc:7

A stride that disagrees between any two of
them corrupts the scrollback silently.

The StreamImageRef identifies the image by its PRIORITY, not by its pool id. A
pool id is an index into an in-memory table and is reused once a sweep reclaims
it, so a frozen row holding one could come back pointing at a different image.
The priority comes from a monotonically increasing counter and is never reused
(/vte/ring/image-pool/reference-rebinds-after-thaw).

The PIXELS get a fourth stream, m_image_stream. When an image is evicted for
memory while rows that name it can still be thawed back, its pixels are written
there rather than thrown away, and read back when the user scrolls to them
(/vte/ring/image/pixels-survive-eviction). It is a VteStream like the other
three, so this costs one more fd and no new on-disk layout.


Why an Image keeps a rectangle
══════════════════════════════

Every pixel decision reads the cells and only the cells. The draw walks the
cells of the rows on screen and places each run from its tile coordinate and
its visual column; a write takes cells back from an image one at a time.
Nothing on that path consults Image::get_top() / get_left(), and it must not,
or a reordered or partially overwritten run gets painted where the cells are
not.

The rectangle an Image stores is a different thing: it is the ring's index of
WHICH ROWS an image occupies. It exists because the ring's rows are not all
cells - at m_writable they stop being memory and become bytes in the text and
attr streams. drop_images_before(), image_is_recoverable() and the spill all
have to answer for exactly those rows, and no cell in memory can answer for
them. find_image_anchor(), which does derive the position from the cells, finds
nothing at all for an image whose rows have all frozen, so an image derived
that way would be freed while the user could still scroll back to it.
/vte/ring/image/rectangle-answers-for-frozen-rows holds the ring in that state.

Deriving it by reading the frozen rows back IS possible, and that is what the
rectangle buys off: drop_images_before() runs once per line the terminal
scrolls, and a scan-based version would thaw rows out of the streams on every
one of those lines. What is checked in is the floor, not a speedup figure:
/vte/ring/image/dropping-a-frozen-image-reads-no-row scrolls an image whose
every row is frozen all the way out and asserts the ring thawed no row doing
it. There is no benchmark in the tree and no timings are quoted here.

The rectangle index is also the only ORDERED structure over images:
m_image_by_top_map is keyed by top row, and drop_images_before() stops at the
first entry keyed at or after the row it is dropping.

The two representations are kept from drifting by two things. Only whole-row
moves update the rectangle, and every such move either re-keys the image in the
same step or runs under a full rebuild of the index. There are two movers.
reanchor_image() is the first: it extracts the map node, sets the top and
re-inserts under the new key, so the rectangle and the key cannot be updated one
without the other. rewrap_images_in_range() is the second, and it leaves the key
stale deliberately - it is a forward walk over the very map the key belongs to,
and re-keying an entry mid-walk would move it under the cursor. What pays for
that is rebuild_image_top_map(), which Ring::rewrap() calls once the walk is
done and before anything reads a key again; the keys are stale between the two
and nothing may read them there. So the rule is not one mover, it is: re-key
with the move, or move under a rebuild that lands before the next key read.

"Nothing may read them there" is a statement about the window, not about
drop_images_before() being the ring's only key-reader - it is not.
shift_images_for_insert() and shift_images_for_remove() compare keys against
the seam, unlink_image_from_top_map() looks an image up by its top row, and
image_invariant_violation() checks every image against the key it is filed
under. What holds is that none of them can run inside the window: the window
is a straight-line stretch of Ring::rewrap(), the ring is not re-entered
there, and the only image call in it is rewrap_images_in_range(). validate()
sits outside it on both sides, which is why it can assert on the keys at all.

That makes the rebuild's POSITION load-bearing, not just its presence, for what
rewrap runs after it. drop_images_before() reads keys rather than images - it is
ordered and stops at the first entry keyed at or after the row it is dropping -
and rewrap() runs it to take in the rows the reflow pushed off the front. Rewrap
numbers the reflowed rows from zero, so a scrolled ring's stale keys are far
larger than the rows the images now sit on, and that early exit fires on the
first entry and drops nothing. /vte/ring/rewrap-drops-before-the-map-is-rebuilt holds the order:
move that call above the rebuild and an image stays resident on rows that have
left the ring.

And the agreement is not assumed. image_invariant_violation() checks it in both
directions: every cell naming an image sits where that image's rectangle puts
it, and every image the writable rows can answer for still has a cell.


Rewrap
══════

Ring::rewrap() rebuilds the ROW stream only. The text and attr streams are not
rewritten, so the image reference and the U+FFFC that a cell carries survive
reflow without rewrap knowing anything about them: the reference is in the attr
stream, the tile coordinates are relative to the image, and the cell comes back
out of the same bytes it went in as. That much is free.

The ring's own index is not free, and rewrap does three explicit things for it
(all under WITH_SIXEL in Ring::rewrap):

  - drop_images_torn_by_rewrap() runs FIRST, before anything is re-anchored, so
    the walk that follows only ever sees survivors. An image is a rectangle of
    physical rows and a reflow is precisely the operation that changes how many
    physical rows a paragraph occupies. re-anchoring moves an image's top row
    and leaves its height alone, which is right only when every covered row
    comes through the reflow the same way the top does - that is, when it is a
    hard-wrapped paragraph of its own that is no wider than the new width. The
    row ABOVE the top is held to the same rule, since a paragraph continuing
    into the image's first row rewrites that row too. Anything else, the image
    is deleted. Keeping it would mean keeping an image that no longer lines up
    with the text it was emitted next to, and text is painted over images, so
    that reads as corruption.

  - rewrap_images_in_range() re-anchors each surviving image's top to its new
    row as the paragraphs are rebuilt.

  - rebuild_image_top_map() then re-keys m_image_by_top_map, and only after
    that can drop_images_before(m_start) run, because it walks the map in key
    order and the keys are the new row numbers only once the map is rebuilt.

/vte/ring/rewrap-with-images covers this.


Pixels and textures
═══════════════════

An Image owns one cairo image surface in CAIRO_FORMAT_ARGB32, which is what
sixel-context.cc produces. It is device-independent: the Image also stores the
cell width and height it was LAID OUT against, fixed at placement, and the draw
addresses the image in that grid rather than in the terminal's current one, so
an image restored from the scrollback keeps the scale it was placed at
(/vte/image/geometry-follows-layout-cell). Display size is computed from the
current cell separately, so the image goes on covering the same cells
(/vte/sixel/image/display-size).

The Images themselves are owned by the Ring, in m_image_map keyed by priority,
with ids handed out by a Ring-owned pool (src/image-pool.hh). An id outlives
the image it named until a sweep confirms no cell still refers to it, which is
what stops a freed image's id from being handed to a new image while a
scrollback cell still points at it (/vte/image/pool/no-reuse-before-sweep,
/vte/ring/image-pool/sweep-sees-cell-references).

On GTK4 a GdkTexture is created lazily from that surface and cached on the
Image, sharing the surface's pixel buffer rather than copying it, so
resource_size() stays truthful and the ring's image GC remains the only
eviction mechanism needed. There is no separate texture cache and no
scale-keyed variant: the texture is one per Image, and scaling to the display
size is the drawing context's job.


═══════════
The prices
═══════════

These are real, they are visible to users, and they are not worked around
anywhere in the tree.


Sideways movement carries the image, but only whole
───────────────────────────────────────────────────

A cell carries its own tile of a picture and the draw reads the picture off the
cells, so cells memmoved sideways take their piece of the image with them for
free. What does not move by itself is the image's own left edge, which every
lifetime rule reads and which validate_image_cells() requires to agree with the
cells - and until Image grew a set_left() there was no way to move it, so every
sideways move deleted the picture outright.

Ring::shift_images_for_scroll() is the rule that moves it. An image every one of
whose CELLS is inside the moving rectangle follows the memmove and keeps them; a
cell the move pushes off the end of the rectangle is dropped exactly as a cell
of text there would be, and the rest of the picture follows clipped. An image
with a cell OUTSIDE the rectangle would be torn - part moved, part standing
still, and no single left edge describing the result - so that one still loses
the cells the move takes.

The partial-region VERTICAL scroll is the same shape and takes the same rule.
With DECSLRM margins narrowing the region, scroll_text_up() and
scroll_text_down() memcpy cells from row to row while the rows themselves stay
put - so the cells carry the picture there too.
Ring::shift_images_for_vscroll() moves such a follower, and it has one thing
more to move than the horizontal rule does: the image's top row is stored
TWICE, as its anchor and as its key in m_image_by_top_map, so a follower is
moved through reanchor_image(), which is the ring's one mover that keeps those
two in step. Skipping the re-key trips image_invariant_violation() with "an
image is filed under a top row it does not start at".

What the vertical rule does NOT do is crop. Sideways, a cell pushed off the end
is dropped and the rest follows clipped, the image's left going to -1.
Vertically that would have to move the top OUT of the region, and two things
forbid it: the FULL-width scroll of the same region goes through
ring_remove()/ring_insert(), where shift_images_for_remove() destroys a
straddler rather than cropping it - so cropping here would make a picture live
or die by whether the margins happened to be full width; and row_t is unsigned,
so an image cropped up past row 0 is filed under a key near ULONG_MAX, which
every ordered walk over m_image_by_top_map steps straight past. So a picture the
region would crop is taken, as before.

The rule hangs off the PRIMITIVES that move the cells, not off a list of
control sequences, and that is the level to state it at: this section used to
carry the list, and the list was wrong - it named ICH, DCH, SL, SR and insert
mode, and had never heard of DECIC, DECDC or DECCRA. The primitives are the
closed part. Three of the four now hand the region to a shift rule before they
move the cells; the fourth still erases over it:

	scroll_text_left(), scroll_text_right()	src/vte.cc, sideways scroll -
						the picture FOLLOWS
	scroll_text_up(), scroll_text_down()	src/vte.cc, else branch only -
						a partial-width region; the
						picture FOLLOWS, but is never
						cropped
	copy_rect()				src/vteseq.cc, over the
						DESTINATION rectangle - still
						an erase

Which operations reach them is then a grep and not a memory. -W prints the
enclosing function, so this ASKS THE TREE for the callers by name and carries
no line numbers to rot when the file moves under it:

	$ LC_ALL=C git grep -W -E '^ +scroll_text_(left|right)\(' -- src/vte.cc src/vteseq.cc | LC_ALL=C grep -E '=Terminal::'
	src/vte.cc=Terminal::cursor_right_with_scrolling(bool fill)
	src/vte.cc=Terminal::cursor_left_with_scrolling(bool fill)
	src/vte.cc=Terminal::insert_char(gunichar c,
	src/vteseq.cc=Terminal::DCH(vte::parser::Sequence const& seq)
	src/vteseq.cc=Terminal::DECDC(vte::parser::Sequence const& seq)
	src/vteseq.cc=Terminal::DECIC(vte::parser::Sequence const& seq)
	src/vteseq.cc=Terminal::ICH(vte::parser::Sequence const& seq)
	src/vteseq.cc=Terminal::SL(vte::parser::Sequence const& seq)
	src/vteseq.cc=Terminal::SR(vte::parser::Sequence const& seq)

So: insert mode via insert_char(), a cursor move that has run into a margin via
the two cursor_*_with_scrolling(), and the sequences DCH, DECDC, DECIC, ICH, SL
and SR. copy_rect() has the one caller DECCRA. Run the grep rather than
trusting this paragraph - the paragraph is the part that decayed before.

This is why the image position has a set_left() alongside its set_top(): the
column moves, and it moves through the ring, which is the only thing that can
keep the edge and the cells saying the same thing.

A full-width row scroll is fine, and a whole-row insert or remove is fine.
Running `ls` in a pane and having something ICH into the row an image sits on
now moves the picture with the text; what is still lost is a picture the move
would TEAR, which is one with a cell outside the moving rectangle - a tall
image under a one-row ICH, most of all.


The byte budget is the whole bound - and it is charged per image, not per pixel
──────────────────────────────────────────────────────────────────────────────

image_gc() (src/ring.cc) evicts while

	m_image_fast_memory_used > m_image_memory_max

and that is the only condition. It used to have a second one, a hardcoded
IMAGE_FAST_COUNT_MAX of 4096 on the NUMBER of resident images, which the public
API - vte_terminal_set_image_limit(), the "image-limit" property, both
documented purely in bytes - never mentioned. An embedder who raised the byte
limit for a screenful of sixels still got eviction at 4097 images with nothing
in the API to say why, and on the alternate screen that eviction did not park
the picture in a stream: spill_image() returns at once when there is no stream,
so there the unmentioned cap DESTROYED images.

The cap was bounding something real, though - the per-image cost the byte
figure does not see. resource_size() is the pixels, which is nearly all of a
photograph and none of a one-band sixel: the Image, the two map nodes holding
it and the surface's own header cost the same whether the picture is 4K or
40x6. Ring::image_cost() is that whole cost, every accounting site goes through
it, and the cap is then redundant.

The overhead figure is sizeof-derived, and its node part is the standard
red-black layout - an estimate of what libstdc++ allocates, not a reading of
it. It only has to be the right order of magnitude; what matters is that it is
not zero, and /vte/ring/image/limit-counts-more-than-pixels asserts exactly
that and nothing finer.


An image evicted before it reaches the scrollback loses the rows still writable
──────────────────────────────────────────────────────────────────────────────

image_is_recoverable() is true only when the image's bottom row is below
m_writable, that is, when every row naming it has frozen. thaw_row() is the one
caller of restore_image(), so a ROW faults its image back exactly when it is
frozen; a row still in the writable window is never thawed and its cells are
drawn straight out of the array.

image_gc() therefore prefers a recoverable victim, and takes an unrecoverable
one only when nothing recoverable is left - otherwise a screenful of images
would raise the limit to whatever it happened to need
(/vte/ring/image/limit-spares-the-unrecoverable).

What that costs is per row, not per image, because the two predicates are at
different scales. A row that had already frozen when the eviction happened
carries the image's priority - append_stream_image_ref() resolved the pool
while the image was still in it - and thaw_row() hands a priority the map no
longer holds to restore_image(), so the row draws its picture again. A row that
freezes AFTER the eviction cannot: note_image_freed() has retired the pool id,
the lookup fails, priority 0 is written, and the row comes back naming nothing.

So an image wholly inside the writable window loses its picture outright, and
an image straddling m_writable loses only the part below it - the part above
reads back from the spill
(/vte/ring/image/unrecoverable-reads-back-where-it-froze). This is why
image_gc() calls spill_image() on every victim without asking
image_is_recoverable() first: for the straddling case that spill is load
bearing. It is unread only for the wholly-writable victim, and even then
bounded rather than leaked - reclaim_image_spill() drops the record, and
advances the stream's tail past it, once the image's bottom row has left the
ring.

image_is_recoverable() being whole-image is thus deliberate imprecision. It
buys the eviction ORDER - an image with any row still writable is the one with
something to lose - and, since every victim is spilled anyway, nothing
recoverable is thrown away by it.

vte_terminal_set_image_limit()'s documentation says this too, in the same
per-row terms.


DECSDM is unimplemented
───────────────────────

Nothing reads sixel display mode - images always scroll. The mode therefore
answers 4, permanently reset, rather than 2, settable. Answering "settable"
would tell a sender it may set a rule we then do not follow. Held by
src/tests/sixel/xtsmgraphics-test.sh, which asserts the reply to

	CSI ? 80 $ p

is

	CSI ? 80 ; 4 $ y
